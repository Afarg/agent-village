## 2026-09-14: `.tab-btn`クラス共有によるサイドバー消失バグ

**症状**: レポートモニター機能（`docs/design/08-report-history.md`）の実装で、ヘッダーに
「オフィス」/「レポート」を切り替える`#view-switcher`を追加したところ、ブラウザ実機確認で
どちらのボタンをクリックしてもサイドバーの「エージェント一覧」「部屋」タブの中身が両方とも
消えてしまう不具合が発生した。

**原因**: `#view-switcher`のボタンに、見た目を流用する目的で既存の`.tab-btn`クラスをそのまま
付けた。ところが`public/js/hud.js`の`initTabs()`は`document.querySelectorAll(".tab-btn")`と
**スコープを絞らずに**クリックハンドラを登録していたため、新設した`#view-switcher`内のボタンにも
このハンドラが二重に付いてしまった。`initTabs()`のハンドラは`btn.dataset.tab`（`"agents"`/`"rooms"`）
を見て`#tab-agents`/`#tab-rooms`の`hidden`を切り替える実装だが、`#view-switcher`のボタンは
`data-tab`を持たず`data-view`しか持たないため、`btn.dataset.tab`が`undefined`になり、
`undefined !== "agents"`・`undefined !== "rooms"`がどちらも`true`と評価され、**両方の
タブパネルが同時に非表示になっていた**。

**対処**: `initTabs()`内のセレクタを`document.querySelectorAll("#tab-bar .tab-btn")`に変更し、
サイドバーのタブバー内のボタンだけにスコープを限定した。修正後、ブラウザで「オフィス」⇔
「レポート」を繰り返し切り替えてもサイドバーの中身が保持されることを確認済み。

**教訓**: 既存のCSSクラス（特に汎用的な名前の`.tab-btn`のようなもの）を「見た目の流用」目的で
別の要素に付ける際は、そのクラス名を**JS側が`querySelectorAll`等でスコープを絞らずに拾っていないか**
を事前に確認すること。CSS上は問題なく見えても、JSのイベントハンドラ登録が意図せず二重に付く形の
不具合は静的なコードレビューだけでは気づきにくく、実際にブラウザで操作して初めて発見できた
（`docs/design/08-report-history.md` §9の実機検証プロセスがなければ、コミット後に気づいていた
可能性が高い）。

## 2026-09-30: 新レイアウトの寸法情報を`/api/rooms`が返しておらず、オフィスが真っ黒になった

**症状**: フェーズ②の2-2（オフィス描画）の初回実機確認で、マップ部分が黒一色になった。コンソールには
`Cannot destructure property 'headerH' of 'this.roomsConfig.metrics' as it is undefined`。

**原因**: `server/src/lib/layout.js`の`computeLayout()`に`metrics`（名札帯・壁の高さ）を追加したが、
`server/src/index.js`の`roomsWithAssets()`は返す項目を**1つずつ列挙して組み立てている**ため、
新しい項目が自動では配信されなかった。

**対処**: `roomsWithAssets()`に`metrics: computed.metrics`を追加した。

**教訓**: `computeLayout()`の戻り値に項目を足すときは、`roomsWithAssets()`の列挙にも足すこと。
また、**Node.jsのサーバーコードを変えた場合、起動中のサーバー（4173番）は再起動するまで古い
APIを返し続ける**。一方で`public/`の画面側ファイルは即座に新しいものが配信されるため、「新しい画面＋古いAPI」
の組み合わせで壊れる。サーバー側の変更を含む作業のあとは、ダッシュボードの再起動が必要。

## 2026-09-30: claude-in-chromeのタブが「非表示」扱いで、Phaserの描画が止まり動作確認できなかった

**症状**: claude-in-chromeで開いたタブでは、状態ファイルを書き換えても、キャラクターが一切動かず
スクリーンショットも変化しなかった。

**原因**: 操作用のChromeウィンドウが背面にあり、`document.hidden === true`になっていた。
そのため`requestAnimationFrame`が0回/秒に止まり、Phaserのゲームループ・トゥイーン・タイマーも
すべて停止していた。ウィンドウのリサイズやページ内クリックでは解除されなかった。
静止画の確認はできるが、移動・アニメーションの確認には使えない。

**対処**: Chrome本体を`--headless=new --remote-debugging-port`で起動し、Node標準の`WebSocket`で
DevTools Protocolを直接操作する小さなスクリプトで検証した（playwright/puppeteerは未導入）。
ヘッドレスではページが常に「表示中」扱いのため、アニメーションが進む。
あわせて、`?debug`付きURLのときだけ`window.__villageScene`を公開するようにし、キャラの座標・
描画順（depth）を数値で確認できるようにした。

**教訓**: Phaserの動き（歩行・吹き出し・状態遷移）を検証するときは、`document.hidden`を最初に確認する。
非表示ならclaude-in-chromeでは検証できないので、ヘッドレスChromeを使う。

## 2026-10-16: `rooms.json`を手で元に戻した編集が無視され、古い内容が書き戻された

**症状**: フェーズ②の2-3（部品ライブラリ）の検証中、テストで部屋名に「!」を付けてから手で元に戻したのに、
画面とファイルの両方に「!」が残った。

**原因**: 2-3で、「APIによる自分の書き込みでは`rooms-changed`（ページ再読み込み）を出さない」ための判定
`isOwnWrite()`を、「ファイルの内容が、サーバーが最後に書いた内容と同じか」で作っていた。
手で元に戻した結果、ファイルがたまたまサーバーの最後の書き込みと同じ内容になったため、自分の書き込みと誤認して無視した。
メモリ上には「!」付きの内容が残り、直後のAPIでの改名がそれをファイルに書き戻していた。

**対処**: 判定を`reloadIfChanged()`に置き換え、「ファイルの内容（JSONとして解釈したもの）がメモリ上の内容と違うか」で
判断するようにした。あわせて、JSONとして読めない手編集では、監視の処理内で例外を出さず、前の設定を保つようにした。
テストに「最後の書き込みと同じ内容に戻す手編集」と「壊れたJSON」の2ケースを追加した。

**教訓**: 「自分の書き込みかどうか」を内容の一致で判定すると、他者の書き込みがたまたま同じ内容になった場合に誤認する。
知りたいのは「誰が書いたか」ではなく「メモリと食い違っているか」なので、それを直接比べる。
また、このバグは操作の順番がたまたま重なったときだけ起きた。スクリーンショットで違和感（部屋名の「!」）に気づけたのは、
数値のチェックだけで済ませず画面も見たため。


## 2026-10-17: 吹き出しの日本語が折り返されず、横に長い1行になっていた（既存の不具合）

**症状**: フェーズ②の2-4（吹き出しの重なり対策）の検証中、吹き出しの幅が273pxになっていた。
`wordWrap: { width: 150 }` を指定していたのに、折り返されていなかった。

**原因**: Phaser の `wordWrap` は、標準では**空白でしか改行しない**。空白のない日本語の文章は1語扱いになり、まったく折り返されない。

**対処**: `useAdvancedWrap: true` を指定した（文字単位でも折り返す）。幅を168pxにし、表示を48文字までに短くした。

**教訓**: 英語前提のライブラリの「折り返し」「単語」系の設定は、日本語で実際に表示して確かめる。
今回は重なりを数値で調べた際に、吹き出しの幅が想定（150px前後）よりはるかに大きいことで気づいた。

## 2026-10-17: 名札・吹き出しの重なり対策が、一部の重なりを見逃していた（2-4の実装中）

**症状**: 6体が同時に発言するテストで、吹き出しが「移動済み」なのに、他の吹き出しと重なったままだった。

**原因**: 待機中のゆれで位置が行き来しないように、一度移した箱だけ余白を4px足して判定していた。
ところが移動先の計算には、足す前の余白（2px）を使っていた。そのため、移した直後の箱がすぐ下の箱に毎回「ぶつかった」と判定された。
同じ位置への移動を上限回数まで繰り返すだけになり、他の箱との重なりを一度も確認していなかった。

**対処**: 配置の方式を作り直した。①元の位置がはっきり空いていれば戻す、②前回の位置がまだ使えれば保つ、
③どちらでもなければ、ぶつかる箱の上・左右・下から空いている最も近い位置を探す。判定と移動先で、同じ余白を使うようにした。

**教訓**: 判定の条件と、それを解消する処理の条件（今回は余白）は必ずそろえる。ずれていると、
「解消したはずなのにまだ条件に当たる」状態が続き、ループが空回りする。

## 2026-10-17: 2-4の重なりテストが、たまたま1回合格しただけで「全項目合格」と報告していた

**症状**: プロジェクト切り替え（2-4b）の後で2-4のテストを回し直したところ、重なりと位置の跳びが3回中2回失敗した。
変更前のサーバーでも同じように失敗したので、2-4のときからあった問題だった。

**原因**: ①テストが「3秒待てば全員が席に着く」前提だった。遠い席のキャラはまだ歩いていて、名札が動き続けていた。
さらに、それを直すために足した「着席待ち」の判定も甘かった。キャラは指示を受けてから0.65秒後に歩き出すので、
その前に休憩所でゆれている状態を「着席済み」と誤って判定していた。
②配置の計算に、待機中のゆれ（最大3px）の途中の位置を使っていた。そのため、隣の2体が逆向きにゆれると判定が行き来した。

**対処**: ①「目的の部屋に着き、ゆれ以外の動きがない」まで待つようにした。
②ゆれる前の位置（`bobBaseY`）で計算し、余白にゆれ幅を足した。②を外すと4回中1回で失敗し、入れると6回中0回だった。

**教訓**: 時間で動く画面（アニメーション）のテストは、1回の合格を証拠にしない。最低でも数回続けて回す。
また、「○秒待つ」ではなく「この状態になるまで待つ」と書く。その「状態」の条件も、途中の状態と取り違えないか確かめる。

## 2026-10-17: プロジェクトを切り替えた直後の状態の変化を取りこぼしていた（2-4bの実装中）

**症状**: 切り替えに失敗して元のプロジェクトに戻った直後に状態ファイルを書き換えても、画面に届かなかった。

**原因**: ファイル監視（chokidar）は、開始してから準備が整う（`ready`）までに少し時間がかかる。その間の書き込みは検知されない。
さらに、状態はその前に読み込み終わっていたので、変化がどこにも反映されなかった。

**対処**: 監視の準備完了を待ってから、定義と状態をもう一度読み直すようにした。

**教訓**: 「読み込む→監視を始める」の順番には、監視が効き始めるまでのすき間がある。監視が準備できてから読み直すと、すき間をふさげる。

## 2026-10-17: 作り直したテスト用プロジェクトで、2-4のテストが「部屋が違う」と失敗した（2-5の検証中）

**症状**: `test_24.js` で、企画担当（planner-a〜c）が企画部屋ではなくテスト部屋に配置され、4回とも失敗した。

**原因**: テスト用プロジェクト（`av_target`）がスクラッチから消えていたので作り直した。その際、エージェントの説明に「テスト用: plan the work」と書いた。
部屋は説明文のキーワードで決まるので、「plan」より先に「テスト」に一致してテスト部屋になった。製品側の不具合ではない。

**対処**: 説明を「dummy: plan the work」に変えた。作り直しの手順を `docs/context_logs/2026-10-16_tests/mkfixture.js` にまとめ、次からは同じ内容で作り直せるようにした。

**教訓**: テスト用のデータを作るときは、その文字列が判定ロジック（ここでは部屋のキーワード）に引っかからないかを確認する。目印のつもりの「テスト」という言葉そのものが、判定の対象になることがある。

## 2026-10-18: 既存テストの再確認で test_24 が「状態ファイルがない」と失敗した（2-6a の検証中）

**症状**: `test_24.js` が、最初の状態ファイルの書き込みで `ENOENT` になり、1項目も実行されなかった。

**原因**: テスト用サーバー（4176番）を起動したまま、ループの中で `mkfixture.js` を実行し、テスト用プロジェクトを消して作り直していた。
状態フォルダはサーバーの起動時に作られるので、作り直したあとには存在しなかった。製品側の不具合ではない。

**対処**: サーバーを止め、「作り直す → サーバーを起動する → テストを複数回実行する」の順にした。作り直しはサーバーの起動前に1回だけ行う。

**教訓**: サーバーが見ているフォルダを、サーバーを動かしたまま消さない。テストの準備（作り直し）は、そのフォルダを使うプロセスを起動する前に済ませる。

## 2026-10-19: test_24 がまた1項目も動かずに止まった（2-6b の検証中）

**症状**: `test_24.js` の1回目が、状態ファイルの書き込みで `ENOENT` になって止まった。2回目以降は合格した。

**原因**: テスト用サーバー（4176番）をバックグラウンドで起動した直後に、テストを始めていた。状態フォルダはサーバーの起動時に作られるので、まだ存在しなかった。製品側の不具合ではない（10-18 の件と同じ種類）。

**対処**: サーバーの起動を `node -e` の fetch ループで待ってから（`ready` を確認してから）テストを始めるようにした。

**教訓**: 別のプロセスに準備させるものは、「起動した」ではなく「準備ができた」を確かめてから使う。

## 2026-10-19: シェルのヒアドキュメントで書いたパッチ用スクリプトが壊れた

**症状**: `cat <<'EOF'` で書いた Node のスクリプトが「unexpected EOF」で失敗した。また、文字列の置換が一致せず止まったこともあった。

**原因**: スクリプトの中に、テンプレート文字列（バッククォート）や `${}`・`\n` が大量に入っていた。シェルと JavaScript の両方のエスケープが重なって、意図した文字列にならなかった。

**対処**: 長いパッチは Write ツールでファイルとして書き、`node` で実行した。小さな変更は Edit ツールで直接行った。

**教訓**: エスケープが二重になる書き方（シェルの中に JavaScript の文字列）は避け、ファイルに書いてから実行する。

## 2026-10-19: `node -e "..."` の中のバッククォートを bash がコマンドとして実行した（引き継ぎの作業中）

**症状**: `project-status.md` に追記する `node -e "..."` を実行したら、追記した文から `docs/design/...` などのパスが消えた。さらに、リポジトリの直下に空のファイルが5つできた（「ステータス:」「題材:」など）。

**原因**: ダブルクォートの中に書いた `` `docs/design/09-ai-office-redesign.md` `` などのバッククォートを、bash がコマンド置換として実行した。設計書 09 がシェルスクリプトとして読まれ、`>` で始まる行（引用の記法）がファイル作成のリダイレクトとして動いた。14行目の構文エラーで止まったため、実行されたのは3〜8行目だけだった。

**対処**:
- git で管理しているファイルに変更がないことを `git status`・`git diff` で確かめた。
- その時刻にできた空ファイル5つを削除した。
- 追記の文は Edit ツールで書き直した。

**教訓**: Markdown のようにバッククォートを含む文字列を、ダブルクォートでシェルに渡さない。文章の追記は Edit／Write ツールか、`<<'EOF'`（引用符つき）のヒアドキュメントで行う。

## 2026-10-19: 歩いている途中で状態が変わると、キャラが違う場所に止まる（既存の不具合）

**症状**: 「作業中 → 待機中 → 作業中」や「割当済み → 待機中」が短い間に続くと、キャラが前の状態の場所に止まった。
たとえば、待機中なのに机に座ったまま、作業中なのに休憩所に立ったまま、になる。
デスクトップ用の配置（設計 14）の検証中に、`test_wide.js` で偶然見つかった。配置とは関係なく、両方の配置で起きていた。

**原因**: `game.js` の `walkTo()` は、前の移動を止めずに新しい移動を始めていた。そのため、前の移動が着いたときの処理（`entry.roomId` の更新）があとから動いた。
また、「!」「✓」のあとの 0.65秒・0.9秒待ってからの移動が、その間に状態が変わっても実行されていた。
さらに、移動の要否を `entry.roomId`（着いたときにしか変わらない）だけで判断していたため、移動中のキャラは「もう着いている」と見なされた。

**対処**:
- 新しい移動は、移動中のものを止めてから始める（止めた移動の到着処理は動かない）。
- 待ってからの移動は、その間に次の状態が来ていたら取りやめる。
- 移動中のキャラは、必ず新しい行き先へ向かわせる。

`test_walk.js`（7通りの切り替えのタイミング × 2つの配置）は、修正前に2件失敗し、修正後は3回続けて全項目合格した。

**教訓**: アニメーションの途中で次の指示が来る場合を考える。到着時の処理を残したままの移動や、待ってから動く処理は、その時点の状態を確かめてから動かす。

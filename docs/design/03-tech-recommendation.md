# 03. 技術選定の提案 — Agent Village Dashboard

`01-visual-concept.md`（見た目）と `02-agent-state-model.md`（データ契約）を実現するための技術構成の提案。本ドキュメントは設計のみで、実装は行わない。

---

## 1. 全体アーキテクチャ（推奨構成）

```
┌────────────────────────────────────────────────┐
│  ローカル監視サーバー (Node.js)                   │
│  ・chokidar で 2 フォルダを監視                   │
│     .claude/agents/*.md   agents/state/*.json   │
│  ・frontmatter パース + JSON パース + 正規化      │
│  ・GET /api/snapshot（初期全量）                 │
│  ・GET /api/events（SSE、差分プッシュ）           │
│  ・静的ファイル配信（ビルド済みフロント）          │
└──────────────┬─────────────────────────────────┘
               │ HTTP + SSE (localhost)
┌──────────────▼─────────────────────────────────┐
│  フロントエンド (ブラウザ)                        │
│  ・ゲーム描画: Phaser 3（タイルマップ+スプライト） │
│  ・HUD/パネル: DOM オーバーレイ（React or 素の TS）│
│  ・02 §5 の表示ステートマシンを実装               │
└────────────────────────────────────────────────┘
```

- **「ファイルを読む責務」をサーバーに集約**する。ブラウザはローカルファイルを継続監視できない（File System Access API は権限・監視の制約が大きい）ため、小さな Node サーバーを挟むのが最も堅い。
- サーバーとフロントは同一リポジトリ内のモノレポ構成（`server/` + `web/`）を想定。配布は `npx agents-app` のような単一コマンド起動を目標にする。

## 2. フロントエンド実装候補の比較

### 2.1 候補比較表

| 候補 | 長所 | 短所 | 本件適合度 |
|---|---|---|---|
| **Phaser 3**（推奨） | タイルマップ・スプライトシート・アニメ・トゥイーン・カメラ・入力が全部入り。Tiled エディタの JSON を直接読める。ピクセルアート向け設定（`pixelArt: true`）一発。情報量が多く実装者を選ばない | バンドルがやや大きい（~1MB）。「ゲームでない UI」には過剰な面も | ◎ タイル移動+アニメ+クリック判定という要件がフレームワーク機能とほぼ 1:1 |
| **PixiJS (v8)** | 軽量・高速な 2D 描画。描画だけ借りて設計の自由度が高い。`SCALE_MODES.NEAREST` でピクセルアート対応 | タイルマップ・アニメステート・経路探索・カメラは自作。ゲームループ設計も自前 | ○ 描画量は小さいので性能メリットは活きにくく、自作コストが先に立つ |
| **HTML5 Canvas 素書き** | 依存ゼロ。内部解像度 320×288 程度なら性能は全く問題ない。学習コストが「Web 標準のみ」 | スプライト管理・アニメ・9-slice・入力ヒットテストを全て自作。長期的に俺々エンジン化する | ○ MVP を最速で出す選択肢としては有効 |
| **DOM + CSS（div にスプライト）** | React 等と統一でき、アクセシビリティ・イベント処理が楽。`image-rendering: pixelated` + CSS steps() アニメで意外と戦える | キャラ数×アニメでレイアウト負荷。カメラ・タイル座標系の管理が不自然。ゲームらしい拡張（エフェクト等）に弱い | △ キャラ 12 体規模なら動くが、伸びしろがない |
| **Kaplay (旧 Kaboom.js)** | 超軽量なゲーム DSL。プロトタイプが速い | エコシステム・保守体制が不安定。大きめの HUD 連携の事例が少ない | △ |

### 2.2 推奨: Phaser 3 + DOM オーバーレイのハイブリッド

- **ゲーム画面（マップ・キャラ・吹き出し）= Phaser 3**。理由: 本件の要件（タイルマップ、4 方向歩行アニメ、タイル単位の経路移動、スプライトのクリック、カメラ固定＋整数スケール）が Phaser の標準機能で完結し、実装者がゲームエンジン自作に時間を使わずに済む。
- **HUD（サイドバー一覧・詳細ログパネル・ヘッダー）= DOM（React 推奨、素の TypeScript でも可）**。長文ログのスクロール・テキスト選択・コピーは DOM が圧倒的に楽。Phaser ⇄ DOM 間は「選択中 agentId」「スナップショット状態」を共有ストア（Zustand 等の軽量なもの）経由で同期する。
- 吹き出しはゲーム内要素（キャラに追従、ピクセルグリッド準拠）なので **Phaser 側**で描く。詳細ログは DOM 側。この分担を崩さないこと（01 §6.2「枠はレトロ、本文はモダン」に対応）。
- ビルドは Vite。`pixelArt: true`、`zoom` は整数、`roundPixels: true` を初期設定に含める。

### 2.3 代替シナリオ

- 依存を最小にしたい場合: Canvas 素書き + 自前ミニループ（MVP 限定と割り切る。P2 以降の演出拡張で Phaser 移行を検討）。
- 既存 React 資産を最大活用したい場合: PixiJS + `@pixi/react`。ただしタイル移動・アニメ管理の自作分を工数に積むこと。

## 3. ファイル変更の検知と反映（サーバー設計）

### 3.1 監視方式の比較

| 方式 | 説明 | 評価 |
|---|---|---|
| **chokidar によるファイル監視（推奨）** | Node の事実上標準。Windows（本環境）/ macOS / Linux で挙動差を吸収してくれる | ◎ 低レイテンシ・低負荷 |
| ポーリング（fs.stat 周期監視） | 1〜2 秒間隔で mtime 比較。実装が単純で確実 | ○ chokidar が不調な環境（ネットワークドライブ等）向けフォールバックとして併載 |
| fs.watch 素使い | OS イベント直結だが、Windows でのリネーム・重複イベントの癖が強い | △ 直接は使わない（chokidar 内部に任せる） |

### 3.2 サーバー内部の処理設計

1. 起動時: 2 フォルダを全走査し、frontmatter（`gray-matter` 等でパース）と状態 JSON を正規化してメモリ上のストアに載せる。`agents/state/` が無ければ空として扱う（エラーにしない）。
2. chokidar で `add` / `change` / `unlink` を購読。
3. **デバウンス 100〜200ms**（同一ファイルのイベントをまとめる）。エディタや書き込み側の「一時ファイル→リネーム」パターンに備え、`awaitWriteFinish`（書き込み完了待ち）を有効化。
4. パース: 失敗したら**前回値を保持**し、警告イベントだけをフロントへ流す（02 §4.1 の破損耐性）。
5. 正規化: ロール推定（02 §3.2）・パレット解決（02 §3.3）はサーバー側で行い、フロントには解決済みの値を渡す。ルール変更の影響範囲をサーバーに閉じるため。
6. 差分イベント（02 §6 のペイロード）を接続中の全クライアントへ配信。

### 3.3 サーバー → フロントの配信方式

| 方式 | 長所 | 短所 | 判定 |
|---|---|---|---|
| **SSE（Server-Sent Events）（推奨）** | 一方向プッシュで要件に十分。自動再接続が仕様組み込み。実装が HTTP だけで済む | 双方向不可（本件は不要）。HTTP/1.1 では同時接続 6 本制限（localhost 単一タブ運用なら無関係） | ◎ |
| WebSocket | 双方向・低オーバーヘッド | 再接続・ハートビートを自作。本件に双方向の要件がない | ○ 将来「ダッシュボードからエージェントに指示を送る」が要件化したら移行 |
| フロントからのポーリング | 最も単純 | 吹き出しの「リアルタイム感」が損なわれる（1〜2 秒遅延） | △ SSE 断絶時のフォールバックとしてのみ |

エンドポイント契約（02 §6 と対応）:

```
GET /api/snapshot        → { agents: AgentCharacter用の正規化データ[], serverTime }
GET /api/events          → SSE。event: "agent-change" / "server-status"、data: 02 §6 のペイロード
GET /api/agents/:id/log  → 詳細パネル用の全量ログ（v2、ndjson 分離後）
```

- フロントは「snapshot で初期化 → events で agentId 単位に上書き」のみ。イベント順序の入れ違いに備え、ペイロードに `updatedAt` を含め、古いイベントは捨てる。
- 接続断は SSE の自動再接続に任せ、再接続成功時に snapshot を取り直す（取りこぼし対策）。ヘッダーの「圏外」表示（01 §6.3）はこの接続状態と連動。

## 4. ピクセルアートアセットの準備方針

### 4.1 段階的プレースホルダー戦略

「絵ができるまで実装が止まる」ことを避けるため、**すべてのアセットに 3 段階の差し替え計画**を敷く。ファイル名とシート構成を最初に凍結し、中身だけ入れ替えていく。

| 段階 | キャラ | マップ | 吹き出し/UI |
|---|---|---|---|
| **P0: ジオメトリ** | 16×16 の単色矩形 + 進行方向を示す 2px の「目」。色は palette.json の main 色 | 床=薄グレー、壁=濃グレー、部屋境界=1px 線、部屋名はプレーンテキスト | ブラウザ標準の div 吹き出しで代用可 |
| **P1: フリー素材/仮ドット** | 汎用 16×16 キャラのフリー素材（後述）を素体として着色スワップ | フリーのインテリアタイルセットで仮組み | 9-slice の自作ドット枠（これは早期に自作。工数小） |
| **P2: 本番自作** | 01 §3 の素体+アクセサリ体系で自作 | 部屋ごとのシンボル家具を含め自作 | エモート・エフェクト類も自作 |

- フリー素材の候補は itch.io / OpenGameArt の CC0 素材（例: 16×16 トップダウン系タイルセット・キャラセット）。**採用時は必ずライセンス（CC0 / CC-BY の別と出典明記義務）を `assets/CREDITS.md` に記録**する。ポケモン実データの抽出素材は使用禁止。
- フォント（美咲フォント / PixelMplus）も同様に CREDITS へ記録（01 §5.3）。

### 4.2 スプライトシート / タイルセットの仕様（凍結対象）

```
assets/
├─ characters/
│   ├─ base-body.png        # 素体シート: 16×16 × (walk 8 + idle 2 + work 2 + talk 2) = 14 コマ
│   ├─ base-body.json       # フレーム定義（Aseprite の JSON export 形式を標準とする）
│   ├─ acc-coder.png        # 役職アクセサリ差分（素体と同グリッド・同コマ数で位置合わせ）
│   ├─ acc-reviewer.png     # …ロールごとに 1 枚
│   └─ ...
├─ tiles/
│   ├─ interior.png         # 床・壁・共通家具のタイルセット（16×16 グリッド）
│   ├─ rooms.png            # 部屋別シンボル家具（アニメ家具はフレーム横並び）
│   └─ office-map.json      # Tiled エディタ形式のマップ（layer: floor / walls / furniture / meta）
│                            #   meta レイヤーに歩行可否・作業スポット・休憩スポットをオブジェクトとして置く
├─ ui/
│   ├─ bubble-9slice.png    # 吹き出し枠 24×24（8px コーナーの 9-slice）×種類分
│   ├─ emotes.png           # ！ ✓ 汗 Zzz … の 8×8 エモート
│   └─ font-8x8.png         # ビットマップフォント（BMFont 形式の .fnt を添付）
└─ CREDITS.md
```

- **色はパレットスワップ前提で描く**: 素体の服部分は「置換用の予約色（例: マゼンタ 2 階調）」で塗り、実行時にシェーダー/カラーマップで palette.json の色に置換する。Phaser なら起動時に Canvas 上でピクセル置換した動的テクスチャを agentId ごとに生成する方式が単純で確実（キャラ数が少ないため性能問題なし）。
- 制作ツールは **Aseprite** を標準（タグ付きアニメ・JSON エクスポート・パレット管理）。無償代替として LibreSprite / Piskel を許容するが、エクスポート形式は上記に合わせる。
- マップ制作は **Tiled**（無償）を標準とし、歩行可否・スポット定義もマップファイル内で完結させる（コード側にマップ座標をハードコードしない）。

### 4.3 アニメ・演出の実装単位

- アニメ名は 02 §5 の visualState と 1:1 で対応させる（`idle` `walk-up/down/left/right` `working` `talking` `celebrating`）。シート更新だけで演出差し替えが済むよう、コード側はアニメ名しか知らない状態を保つ。
- 家具アニメ（PC 画面点滅等）はキャラと独立したタイルアニメとして定義し、部屋の占有状態（誰か作業中か）でオン/オフする。

## 5. リスクと先送り事項

| 項目 | 内容 | 方針 |
|---|---|---|
| 状態ファイルの書き込み主体 | `agents/state/*.json` を「誰が」書くか（Claude Code の hooks か、ラッパースクリプトか）は本設計の範囲外 | 02 §4 のスキーマを契約として先に凍結し、書き込み側は後続プロジェクトで設計 |
| エージェント数のスケール | 13 体以上でマップが飽和 | v2 で休憩所のページング or マップ拡張（01 §2.1） |
| 全量ログの肥大 | 状態 JSON 内ログは 50 件上限 | v2 で ndjson 分離 + `/api/agents/:id/log`（§3.3） |
| ブラウザ直読み構成（サーバーレス） | File System Access API + ポーリングで理論上は可能 | 監視の信頼性が低いため不採用。要望が強ければ実験ブランチで検証 |

## 6. 推奨構成まとめ

- 描画: **Phaser 3（pixelArt モード）+ DOM オーバーレイ（React）**、ビルドは Vite。
- 同期: **Node.js + chokidar + SSE**。snapshot + 差分イベントの 2 段構え。正規化（ロール推定・色解決）はサーバー側。
- アセット: **Aseprite + Tiled** を標準ツールとし、P0 ジオメトリ → P1 フリー素材 → P2 自作の 3 段階差し替え。シート構成とファイル名を先に凍結する。
